# Day 4 Quiz: Answers

1. Define the benchmark and metric (with variance control) → profile (where, then why: HW counters) → hypothesis + the smallest change → measure A/B → guard it in CI and communicate the before/after with the trade-offs.
2. Reproduce on a pinned benchmark and confirm it's real (repeat runs, variance). Bisect the merge range (automated `git bisect run` with a timing threshold). `perf diff` / flame graphs of old vs new. Inspect the offending change (accidental copies, lost inlining, O(n²), extra allocations, a lock). Fix or revert. Add a perf gate so it can't recur.
3. `perf stat` = aggregate counters (cycles, instructions, IPC, cache/branch misses) for the whole run. `perf record` = sampling with stacks → `perf report` shows where the time goes. Flame graph: the x-axis is the proportion of samples (not time order), the y-axis is stack depth. Wide towers = hot call paths.
4. Classes: UB exploited by the optimizer (uninitialized vars, OOB, signed overflow, strict aliasing, lifetime), data races with timing changes, ODR/ABI mismatches between objects built differently, and compiler flags like `-ffast-math`. Actions: build release **with `-g`** + get a core dump/backtrace; run ASan/UBSan (and TSan) builds; turn on `-Wall -Wextra` + static analysis; bisect by optimization level or per-file flags.
5. Memory is still *reachable*, so it's not a leak: unbounded caches/containers, a growing history or undo log, fragmentation (RSS ≫ live bytes), or the allocator not returning memory to the OS. Tell by taking heap profiles over time (heaptrack/massif) and diffing snapshots, comparing live bytes (from allocator stats, `malloc_info`) vs RSS, and trying jemalloc/tcmalloc or `malloc_trim`.
6. Non-Uniform Memory Access: each socket/NUMA node (and on EPYC, each CCD group) has local memory. Remote access costs more latency and less bandwidth. A tool whose main thread allocates everything (first touch) then gets processed by 64 workers on other nodes suffers. Fixes: first-touch by the workers, interleaving (`numactl --interleave`), thread pinning, per-node pools, partitioning the data by thread.
7. Speedup ≤ 1 / (s + (1−s)/N). With s = 0.05, N = 128: 1/(0.05 + 0.95/128) = 1/(0.0574) ≈ **17.4×**. The serial part dominates, so attack it first.
8. Hash/pointer-order iteration → sort by stable IDs. Race-dependent "first result wins" / work stealing order → deterministic partitioning and merge in a fixed order. Floating-point reduction order → fixed-order reductions per partition. (Also: uninitialized memory → sanitizers; time-seeded RNG → fixed seeds per task.)
9. Text (code) → rodata → data (initialized globals) → BSS (zeroed globals) → heap (grows up) → … mmap region (shared libs, big allocations) … → stack (grows down) → kernel space.
10. The MMU finds no valid translation → trap to the kernel. **Minor**: the page is already in memory (first touch of an anonymous page → zero page, a COW copy, or a page cache hit) → just map it. **Major**: the data must be read from disk/swap → I/O wait. An invalid address → SIGSEGV.
11. Only the calling thread exists in the child. Locks held by the other threads (e.g. the malloc arena lock, logging mutexes) stay locked forever → the child can deadlock on its first `malloc`/`printf`. Only async-signal-safe calls between `fork` and `exec`; prefer `posix_spawn`. With 100 GB of RSS, even COW page-table copying is expensive → `vfork`/`posix_spawn`.
12. (a) SoA tables with **32-bit ids** instead of pointer-linked objects; (b) **CSR** for net→pins and cell→pins; (c) **interned / hierarchical names** (plus hierarchical storage of module definitions). Estimate: ~400M pins × ~11 B ≈ 4.4 GB, ~100M cells × ~17 B ≈ 1.7 GB, plus names and the timing side tables.
13. PathFinder with deterministic net ordering. In each iteration, form batches of nets with non-overlapping bounding boxes (or region partitions); route a batch in parallel with thread-local occupancy deltas; merge the deltas in a fixed order at the batch barrier; update the costs; repeat. Per-thread A* scratch (the timestamp trick). Verify by running with 1/8/32 threads and diffing the results.
14. A serialized snapshot of the full in-memory design at a flow stage (netlist + placement + routing + constraints), used to resume flows, share with debug/customers, and do incremental runs. Concerns: versioning and backward compatibility, size (compression), load/save speed (binary, mmap-able arrays), completeness (every piece of state gets saved: the classic bug), determinism of re-load, and security/IP (encrypted blocks).
15. Inclusive (L1 ⊂ L2) simplifies coherence (L2 acts as a snoop filter) but wastes capacity. Exclusive uses the total capacity but has complex movement between levels. Write-through keeps the lower level consistent (simple, more write traffic); write-back reduces traffic but needs dirty tracking and write-back on eviction.
16. Situation: the architecture choice (e.g. threads vs processes for partitioned solving). Task: I owned the delivery. Action: prototyped both, measured (memory isolation, crash containment, speedup), presented the data, and **disagreed and committed** on the parts where the data was inconclusive. Result: the chosen design + numbers + the relationship kept intact. (Use your own real story; see 08-Lead.)
17. Be concrete and responsible. For example: I use an assistant for exploratory code reading in a 2M-line codebase, for writing test scaffolding, and for regression-triage summaries (my personal tooling cut my triage from hours to minutes). I verify everything: I never paste proprietary code into unapproved tools, I review generated code like any other PR, and I measure whether it saves time. As a lead: team guidelines, sharing prompts/playbooks, and tracking adoption.
18. (a) **Domain fit**: EDA tools at scale plus formal/C++ performance experience map directly to Vivado's QoR/runtime challenges (and to HLS verification). (b) **Closer to silicon**: building the toolchain for AMD's own FPGAs/adaptive SoCs, where software quality directly shapes the product. (c) **The Lead scope**: driving performance initiatives across a team, which is the role I've been growing into (the decoupling effort, the licensing program, coverage ownership).
19. Structured code reviews with teaching comments and a shared "review checklist" for perf/C++ pitfalls. Pairing on hard debugging sessions. Delegating an owned sub-area with clear success metrics (instead of tasks). Brown-bag talks. Growth plans with stretch assignments.
20. Measure first: a per-design runtime breakdown and the critical path of the suite. Then: parallelize across the farm (sharding, priority scheduling), tier the suite (a fast smoke subset for merge gating, the full suite nightly, the heavy one weekly), cache unchanged stages (checkpoints), remove redundant designs by coverage analysis, and speed up the tool itself (the perf work). Set a target (e.g. under 4 hours) with owners, then report the progress.
